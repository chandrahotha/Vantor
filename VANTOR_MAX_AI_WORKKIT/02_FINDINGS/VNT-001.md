# VNT-001 — Live invoice approval checks only the current invoice quantity, not cumulative invoiced quantity.

> **Source of truth:** Current VANTOR archive re-audit

## Classification

- **Severity:** High
- **Status:** Verified
- **Confidence:** High
- **Category:** Financial integrity

## Location

`backend/app/services/purchase.py:123-153 (`three_way_match`); backend/app/routers/purchase.py:455-480 (`approve_invoice`)`

## Evidence

`three_way_match()` sums receipts into `received` but checks each current invoice line with `il.quantity > received[...]` at lines 140-148. It does not sum quantities from previously approved invoices. `approve_invoice()` calls this function at line 465 and then creates the actual spend transaction at lines 469-472.

## Impact

The same received quantity can potentially support multiple separately approved invoices. This can duplicate financial liability and spend ledger entries.

## Required remediation

Use one canonical matcher that receives all prior invoice lines and enforces: approved prior quantity + current quantity <= received quantity, plus repeated-line protection. Enforce the same invariant atomically under a row-level lock/serialization boundary.

## Required invariant / acceptance

For every PO line: approved_invoice_qty + current_invoice_qty <= received_qty <= ordered_qty. Also one actual spend transaction per approved invoice.

## Required tests

Unit: cumulative partial invoices; exact boundary; overage. Integration: two invoices against same receipt. Concurrency: simultaneous approval of two invoices. E2E: partial invoice A then invoice B. DB: unique actual ledger key.
