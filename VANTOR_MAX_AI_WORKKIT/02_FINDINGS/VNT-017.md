# VNT-017 — Broadcast unread counts are intentionally capped and can be approximate at high volume.

> **Source of truth:** Current VANTOR archive re-audit

## Classification

- **Severity:** Medium
- **Status:** Verified
- **Confidence:** High
- **Category:** Notifications

## Location

`backend/app/routers/notifications.py:50-108`

## Evidence

The unread-count query scans at most `BROADCAST_SCAN_CAP = 500` broadcast rows and returns `unreadCapped=true` when saturated.

## Impact

The badge can show a lower numeric count than reality, although the API honestly flags the cap. At large scale the UX becomes approximate.

## Required remediation

Move broadcast read state to a normalized recipient/read table or use per-user notification materialization. Maintain exact unread counts through transactional counters or a scalable fanout strategy.

## Required invariant / acceptance

The remediation must preserve tenant isolation, auditability, authorization correctness and deterministic behavior.

## Required tests

501+ broadcasts; concurrent read/insert; exact unread count under pagination; multi-tab consistency.
