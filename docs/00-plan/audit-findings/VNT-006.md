# VNT-006 — Idempotency is replay-safe after completion but not atomic against concurrent duplicate requests.

> **Source of truth:** Current VANTOR archive re-audit

## Classification

- **Severity:** High
- **Status:** Verified
- **Confidence:** High
- **Category:** Reliability / idempotency

## Location

`backend/app/core/idempotency.py:98-139`

## Evidence

The middleware checks for an existing key, executes the request at line 126 when no record exists, then stores the response afterward at line 136. `_remember()` handles a unique-key race but only after both business operations may already have executed.

## Impact

Two simultaneous requests with the same idempotency key can both create business side effects.

## Required remediation

Atomically claim the key before executing the handler using Redis SET NX or a database unique insert with an in-progress state. Other callers should wait/replay or return a deterministic 409 while the first request is in flight. Handle abandoned claims with TTL.

## Required invariant / acceptance

The remediation must preserve tenant isolation, auditability, authorization correctness and deterministic behavior.

## Required tests

Concurrent identical POSTs; handler failure; client timeout then retry; process crash after claim; response replay fidelity.
