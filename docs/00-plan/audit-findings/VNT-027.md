# VNT-027 - Spend ledger uniqueness is enforced mainly by workflow state rather than database uniqueness.

> **Source of truth:** Current VANTOR archive re-audit

## Classification

- **Severity:** Medium-High
- **Status:** Strong static finding
- **Confidence:** High
- **Category:** Ledger integrity

## Location

`backend/app/models/spend.py and backend/app/routers/purchase.py:366-380,455-480`

## Evidence

`SpendTransaction` stores commitment/actual transactions but no unique constraint tying `kind=commitment` to one PO or `kind=actual` to one invoice. Workflow transitions are susceptible to concurrency windows.

## Impact

Duplicate financial ledger rows can be created if send/approve operations race or are retried across process boundaries.

## Required remediation

Add unique business keys such as `(tenant_id, kind, po_id)` for commitment and `(tenant_id, kind, invoice_id)` for actual where model semantics allow; handle conflicts deterministically and reconcile ledger-to-source daily.

## Required invariant / acceptance

The remediation must preserve tenant isolation, auditability, authorization correctness and deterministic behavior.

## Required tests

Concurrent PO send; concurrent invoice approve; retry after network timeout; ledger reconciliation.
